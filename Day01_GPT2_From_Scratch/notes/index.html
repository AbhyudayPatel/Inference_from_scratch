Part 1 — The .safetensors format, dissected

The entire format fits in one diagram. No compression, no code, no magic.

The whole spec: header-length prefix → JSON directory → raw tensor bytes. data_offsets are relative to the buffer start, not the file. That single detail is the classic hand-parser bug.

One header entry, dissected

{
  "h.0.attn.c_attn.weight": {
    "dtype":        "F32",          // each number = 4 bytes
    "shape":        [768, 2304],   // 1,769,472 elements
    "data_offsets": [b, e]       // e − b = 7,077,888 bytes
  }
}
invariant: elements × bytes-per-element = e − b 1,769,472 × 4 = 7,077,888 ✓ ← always check this; it catches corrupt parses instantly

The parser — full code

code/inspect_safetensors.py — core loader
import json, struct
import numpy as np

def load_safetensors(path):
    with open(path, "rb") as f:
        (n,) = struct.unpack("<Q", f.read(8))      # ① header length
        header = json.loads(f.read(n).decode("utf-8"))  # ② JSON directory
        buffer = f.read()                             # ③ the raw buffer

    metadata = header.pop("__metadata__", None)     # ④ not a tensor!

    tensors = {}
    for name, info in header.items():
        begin, end = info["data_offsets"]            # ⑤ relative to buffer
        raw  = buffer[begin:end]                      # ⑥ slice the bytes
        arr  = np.frombuffer(raw, dtype=DTYPE_MAP[info["dtype"]])  # ⑦ zero-copy view
        tensors[name] = arr.reshape(info["shape"])    # ⑧ interpret as matrix
    return tensors, metadata

…line by line

LineWhat it doesWhy it matters
① struct.unpack("<Q", read(8)) Reads 8 raw bytes, interprets as unsigned 64-bit int, little-endian (< = LE, Q = u64). The trailing comma in (n,) unpacks the 1-tuple. This is the only framing the format has. Get endianness wrong and N is astronomically wrong → instant garbage.
② json.loads(read(n)) Reads exactly N bytes → UTF-8 string → Python dict. bytes → text → dict. Three representations of the same header; know which one you're holding at each step.
③ buffer = f.read() Everything after the header = the tensor warehouse. Because we already consumed 8+N bytes, buffer[0] is file offset 8+N. That's why offsets "just work".
④ header.pop("__metadata__") Removes the special non-tensor entry ({"format": "pt"} here) so the loop only sees real tensors. Forget this and you'll try to "reshape" a metadata dict. Classic crash #1.
⑤ data_offsets [begin, end) byte range of this tensor inside the buffer. Relative to buffer start, not file start. Absolute = 8 + N + begin.
⑥ buffer[begin:end] Python slice of bytes → a copy of this tensor's byte range. Slicing bytes copies; that's fine at this scale. (memmap version = exercise.)
⑦ np.frombuffer(raw, F32) Reinterprets each 4-byte group as one float32. Zero-copy — wraps the bytes, doesn't transform them. Bytes aren't numbers until a dtype gives them meaning. This is the single most systems-y idea of the day.
⑧ reshape(shape) 1-D array of 1,769,472 floats → (768, 2304) matrix. A view, still no copy. The matrix doesn't exist on disk — only bytes + the metadata's claim about shape. Shape is interpretation.
Parse pipeline. Total: ~15 lines of real code. You can now parse any HF checkpoint on earth.

The 4 discoveries (verified output)

Each one is a permanent lesson about how checkpoints and engines really work.

Discovery ① — 160 tensors, not 148: checkpoints contain junk

✔ Found in the wild
The file holds 160 tensors. 12 of them — h.X.attn.bias, shape (1,1,1024,1024), 4 MB each — are precomputed causal-mask buffers, not parameters. That's 48 MB (~9%) of dead weight in a 548 MB file.

HF saves registered buffers alongside weights, so the mask got serialized too. vLLM / TRT-LLM / SGLang skip tensors like this at load time and build masks inside their kernels. Reading a checkpoint professionally means knowing what to ignore.

Discovery ② — the "124M model" has 137M values on disk

values on disk = 137,022,720 mask buffers (not params) = 12 × 1,024 × 1,024 = 12,582,912 ───────────────────────────────────────────────────────────── real parameters = 124,439,808 ← the "124M" in GPT-2 hand-derivation from config (the checksum): wte 50,257 × 768 = 38,597,376 wpe 1,024 × 768 = 786,432 blocks 12 × 7,087,872 = 85,054,464 ln_f 2×768 = 1,536 ───────────── 124,439,808 ✓ exact match memory identity: 137,022,720 × 4 bytes = 548,090,880 B = exact file size ✓
One embedding matrix (wte) ≈ 45% of a block stack's size — and it doubles as the output projection (weight tying, Part 3).

Discovery ③ — the names ARE the architecture

Weight fusion is not an engine trick — it's already in the checkpoint. Engines just exploit it harder.

Discovery ④ — the Conv1D trap

⚠ Error case #1 — caught live
GPT-2 stores linear weights as (in, out) — the transpose of PyTorch's nn.Linear convention (out, in). Muscle memory says x @ W.T. The shapes refuse.
The dangerous variant
c_attn is (768, 2304) so a wrong transpose fails loudly. But c_proj is (768, 768) — square. A wrong transpose there multiplies fine and produces silent garbage. GPT-2-specific too: Llama-family checkpoints use plain Linear conventions. Log both in notes/errors.md.

How the world actually loads weights

Nobody in production writes buffer = f.read(). Our parser is level 0 of a ladder — every rung above is the same format, loaded more lazily. The format barely changes; the laziness is the engineering.

Same bytes, same JSON header at every rung. What changes is when data moves and whose memory it lands in.

Rung 1–2 · What the official safetensors library does

the library way — Rust core, mmap'd, lazy
from safetensors import safe_open          # Rust core (memmap2), not Python

with safe_open("models/model.safetensors", framework="pt") as f:
    f.keys()                          # ① header only — instant, no data read
    w = f.get_tensor("wte.weight")      # ② mmap'd view → ONE tensor materialized
    s = f.get_slice("wte.weight")       # ③ lazy slicer: read PART of a tensor
    s[:, :384]                          #    ← how tensor-parallel shards load
  • mmap, not read: the file is mapped into virtual memory; tensor bytes are OS page-cache pages, faulted in only when touched. "Loading" returns instantly.
  • Zero-copy: the torch/numpy tensor points at those pages directly — no intermediate buffer, no Python loop over tensors.
  • Validated: header size capped (100 MB), offsets bounds-checked — pickle's code-execution hole designed away.
Why engines love this format: the JSON header you parsed by hand is the only eager read. Everything else is page faults.

Multi-GPU loading isn't "load then split" — it's split at the byte range. Your data_offsets field is what makes this possible.
The most radical answer to "how do you parse weights fast": don't. Compile them away.
Why pickle died
torch.load on a .bin/.pt unpickles — and pickle can execute arbitrary code hidden in the file. PyTorch ≥ 2.6 defaults to weights_only=True for this reason. safetensors won because a JSON + raw-bytes format is incapable of executing anything — you proved that by hand today: nothing in your parser could run code.
The one-line takeaway
Model loading is a memory-management problem, not a parsing problem. The format barely matters; when bytes move and whose memory they land in is the entire game — the same game as KV-cache paging, as you'll see on Day 2.

Inside an engine loader — the 4-hook protocol

Strip away the industrial plumbing and every loader — vLLM, SGLang, TRT-LLM's converter — is the same four hooks. We reimplemented them against our GPT-2 file in code/mini_vllm_loader.py and verified each one.

GPT-2 numbers from our run: 160 enumerated → 12 filtered → 148 placed + 1 tied, 498 MB moved at 0.77 GB/s (CPU, cold cache).

Hook 4 in detail — the two mechanisms GPT-2 hides from you

GPT-2 ships QKV pre-fused, so its loader path looks boring. Llama-class checkpoints ship separate q_proj / k_proj / v_proj — and multi-GPU serving needs sharding. Both are the same hook with different arguments:

vLLM's stacked_params_mapping = [("qkv_proj", "q_proj", "q"), ("qkv_proj", "k_proj", "k"), …] is literally this picture as data.
Verified in our run: both TP slices concatenate back to the exact original tensor.

And TRT-LLM? Same hooks — but at build time, plus a compiler

TRT-LLM runs hooks 1–3 like everyone, but "place" means bake into a compiled graph: fusion and quantization decisions frozen into the engine. Serving then does zero name/layout work. SGLang, by contrast, uses vLLM's runtime loader almost verbatim — their differences are in scheduling (RadixAttention), not loading.
The mental compression
An engine loader is a compiler for names and layouts: checkpoint-space → engine-space. Four hooks; the only real content is the mapping table (per model family) and what "place" does (copy / fuse / slice / cast / compile). When you later read vLLM's gpt2.py or llama.py loader, you'll now recognize all four hooks on sight.
